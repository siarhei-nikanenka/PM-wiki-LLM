# Риск-мастерская — примерные ответы по кейсам

Не часть основной ингест-схемы (raw → wiki → schema) — ключ для преподавателя к [[pm-17-risk-management-workshop]]. Не эталон («правильных» рисков в открытом кейсе не существует), а ориентир: что засчитывать как разумный ответ, куда подталкивать группу вопросами, если она застряла. Опирается на [[risk-management]] и [[contract-types]].

Общий принцип проверки: риск сформулирован по схеме «причина → событие → последствие», лежит в верной RBS-категории, его место в матрице обосновано (не наугад), а стратегия реагирования соответствует и риску, и типу контракта — не просто названа.

## Группа A — Consero (Fixed Price)

**Риски (RBS):**
- *Технический* — если backend/API строит отдельная команда на Salesforce → то интеграция задержится или API окажется не тем, что ожидалось → то iOS-команда простаивает или переделывает клиентскую логику за счёт фиксированного бюджета часов.
- *Технический* — если Salesforce — платформа заказчика со своими ограничениями (лимиты API, кастомизация) → то ограничения вскроются поздно → то потребуется архитектурный компромисс сверх сметы.
- *Управленческий* — если фичи вроде «чат между гостями» описаны в брифе очень общо → то в ходе разработки заказчик уточнит/расширит понимание фичи → то возникнет scope creep, требующий формального Change Request и портящий отношения с клиентом.
- *Коммерческий* — если цена и объём зафиксированы, а 600 часов на iOS-приложение с авторизацией, чатом, расписанием и персональным маршрутом — сжатая оценка → то бюджет часов истощится до сдачи всех фич → то риск полностью на исполнителе (природа Fixed Price), придётся либо доделывать бесплатно, либо конфликтовать.
- *Внешний* — если дата конференции жёстко фиксирована и не переносится → то любая задержка разработки → то нет буфера для сдвига срока.

**Топ-3 / матрица:** (1) интеграция с Salesforce-API чужой команды — вероятность средняя-высокая, воздействие высокое (блокирует весь фронт); (2) недооценка объёма в 600ч — вероятность средняя, воздействие высокое (маржа проекта); (3) scope creep из-за общих формулировок — вероятность средняя, воздействие среднее-высокое.

**Реагирование:**
1. Интеграция API → **снижение**: зафиксировать контракт/спецификацию API с backend-командой до старта, параллельная разработка на моках, регулярные синки. Ответственный — PM + tech lead.
2. Недооценка объёма → **принятие активное**: резерв в оценке (10–50% для Fixed Price, см. [[cost-management]]) плюс приоритизация MVP-функционала, если резерв уже некуда закладывать.
3. Scope creep → **уклонение**: детальный SRS/ТЗ до старта разработки + формальный Change Request на любое уточнение сверх зафиксированного.

**Защита:**
- Главный риск — интеграция с чужой Salesforce-командой: самое высокое воздействие, срывает весь фронт разработки, а не одну фичу.
- Убивает проект — конфликт по scope без формального change control: либо бесплатные доработки съедают маржу, либо портятся отношения с ключевым клиентом уровня «топ-менеджеров».
- Контракт → Fixed Price перекладывает все финансовые последствия на исполнителя, поэтому реакция на все риски проактивная (снижать вероятность заранее), а не «принять и посмотреть» — в T&M те же риски были бы менее критичны для PM.

## Группа B — AF Gruppen (Fixed time / Fixed budget / Flex scope)

**Риски (RBS):**
- *Технический* — если ERP и три мобильных приложения (Basic/Driver/Controller) разрабатываются параллельно → то велика архитектурная сложность интеграции единой системы данных → то возможны нестыковки API/данных между модулями, найденные поздно.
- *Управленческий* — если у проекта три независимых направления (HR, Projects, Drivers/Controllers) и четыре стейкхолдера с разными приоритетами → то у каждого направления свои ожидания по важности → то конфликт при распределении команды и бюджета между направлениями.
- *Управленческий* — если команда большая (12 000 ч / 8 мес ≈ 15–20 человек параллельно) → то координация между под-командами усложняется → то узкие места на общих компонентах (единая аутентификация, общая БД).
- *Коммерческий* — если контракт FFF (объём — единственный изменяемый параметр) → то заказчик может настаивать на добавлении функциональности без понимания, чем придётся пожертвовать → то конфликт ожиданий по итоговому набору фич при неизменных сроке и бюджете.
- *Внешний* — если проект цифровизует персональные данные водителей/контролёров в Норвегии → то применяется европейское регулирование защиты данных → то несоблюдение требований по хранению personal data грозит юридическими санкциями.

**Топ-3 / матрица:** (1) конфликт ожиданий по scope при FFF — вероятность высокая, воздействие высокое (может сорвать launch date); (2) конфликт приоритетов четырёх стейкхолдеров — вероятность высокая, воздействие среднее-высокое; (3) требования по защите персональных данных — вероятность средняя, воздействие высокое (юридические последствия серьёзны).

**Реагирование:**
1. Конфликт ожиданий по scope → **снижение**: формальная приоритизация (MoSCoW/WSJF, см. [[prioritization]]) и регулярная синхронизация с заказчиком о том, что переносится в следующий релиз при превышении бюджета — прямой механизм FFF.
2. Конфликт приоритетов стейкхолдеров → **снижение + эскалация**: единый канал коммуникации со всеми четырьмя стейкхолдерами; спорные вопросы вне полномочий PM эскалируются к Harald Juland (Head of Innovation) как решающему голосу.
3. GDPR/персональные данные → **передача/снижение**: юридическая экспертиза на этапе Design, compliance-требования закладываются в архитектуру с самого начала, а не постфактум.

**Защита:**
- Главный риск — конфликт ожиданий по scope: самая высокая вероятность (естественное следствие FFF с несколькими стейкхолдерами) и высокое воздействие.
- Убивает проект — не техническая неудача, а политический провал: один из четырёх стейкхолдеров (например, HR Director) чувствует, что его направление урезали в пользу другого, и теряет доверие к проекту.
- Контракт → FFF делит риски между клиентом и исполнителем, поэтому стратегия по умолчанию — не «молча принять на свой счёт» (как пришлось бы в Fixed Price) и не «просто выставить счёт» (как в T&M), а формально управлять объёмом через регулярные явные переговоры.

## Группа C — Archery Game (Time & Materials)

**Риски (RBS):**
- *Технический* — если требуется мультиплатформенная сборка (mobile → PlayStation/Xbox) на Unity3D → то консольная сертификация Sony/Microsoft — отдельный, часто непредсказуемый по срокам процесс → то релиз на консолях может задержаться независимо от готовности кода.
- *Управленческий* — если в проекте впервые нужны роли, которых раньше не было в команде (геймдизайнер, 3D-модельеры) → то придётся нанимать или наращивать компетенции с нуля → то риск задержки старта или снижения качества контента.
- *Коммерческий* — если контракт T&M на 50 000 ч без жёсткого потолка, а заказчик — не эксперт в геймдеве (владелец розничной сети) → то он может не понимать реальную стоимость мультиплатформенной разработки → то неконтролируемый рост бюджета (burn rate) и недовольство заказчика счетами при формальной правоте исполнителя.
- *Внешний* — если цель проекта — маркетинговый инструмент для сети, а не самостоятельный игровой продукт → то успех измеряется бизнес-метриками сети, а не игровыми → то технически успешная игра может быть признана «неудачной», если не даст ожидаемого маркетингового эффекта (нечёткость целей).
- *Управленческий* — если один из стейкхолдеров (маркетолог в геймдеве), а не сам разработчик, формирует требования к геймплею → то они могут постоянно меняться или быть нереалистичными по объёму на бюджет и срок.

**Топ-3 / матрица:** (1) неконтролируемый рост бюджета/burn rate — вероятность высокая при T&M без потолка и неопытном в теме заказчике, воздействие высокое; (2) сертификация консолей — вероятность средняя-высокая (внешний неконтролируемый процесс), воздействие высокое для даты релиза; (3) нечёткие/меняющиеся требования к геймплею — вероятность высокая, воздействие среднее.

**Реагирование:**
1. Рост бюджета → **снижение**: PM еженедельно прозрачно отчитывается о burn rate (прямая обязанность PM в T&M, см. [[cost-management]]), регулярные демо и сверка ожиданий «бюджет vs сделанный объём».
2. Сертификация консолей → **принятие активное (резерв по срокам)**: временной буфер под цикл сертификации закладывается отдельно от mobile-релиза, не обещать одновременный запуск на всех платформах.
3. Нечёткие требования к геймплею → **снижение**: профильный геймдизайнер на стороне заказчика как консультант с самого старта, фиксация core game loop / vertical slice до масштабирования разработки на все платформы.

**Защита:**
- Главный риск — рост бюджета/burn rate: самая высокая вероятность именно из-за сочетания T&M без потолка и неопытного в отрасли заказчика.
- Убивает проект — заказчик теряет доверие к тратам (burn rate растёт быстрее видимого прогресса) и останавливает финансирование до релиза; при T&M ничего формально не гарантирует продолжение оплаты.
- Контракт → T&M перекладывает риски на клиента, поэтому задача PM не «уложиться в бюджет любой ценой» (как в Fixed Price), а обеспечить прозрачность трат, чтобы клиент мог сам управлять решением «продолжать/остановить».

## Кейс 4 (запасной) — Universal Pictures (Dedicated Team / Support SLA)

**Риски (RBS):**
- *Технический* — если приложение таргетирует iOS 9, а Apple продолжает обновлять требования App Store → то новые версии iOS/устройства могут перестать поддерживать старый код или отклонять обновления → то приложение рискует стать неработоспособным или недоступным для публикации в течение контракта.
- *Управленческий* — если команда занята только частично (4 ч/день) → то переключение контекста между проектами снижает знание кодовой базы → то повышенный риск ошибок при доработках legacy-кода, который команда помнит не полностью.
- *Коммерческий* — если контракт Dedicated Team/support SLA изначально закладывает минимальные резервы на риски → то любой незапланированный крупный баг или требование выходит за рамки бюджета часов → то PM вынужден либо выбивать доп. часы, либо urgent-фиксы вытесняют плановые «minor improvements».
- *Внешний* — если заказчик — крупная киностудия, для которой приложение второстепенно, а единственный стейкхолдер (Michael Weiss) — менеджер площадки, не топ-менеджмент → то решения по проекту принимаются медленно → то риск задержек согласований.

**Топ-3 / матрица:** (1) устаревшая iOS 9 → вероятность высокая со временем (Apple ежегодно ужесточает требования App Store), воздействие высокое (приложение может перестать работать/публиковаться); (2) частичная занятость → потеря контекста — вероятность средняя-высокая, воздействие среднее; (3) минимальные резервы контракта — вероятность средняя, воздействие среднее-высокое.

**Реагирование:**
1. Устаревшая iOS 9 → **эскалация**: выносится на уровень выше как решение, требующее согласия заказчика и отдельного бюджета — обновление минимальной версии iOS не решается в рамках текущего SLA.
2. Частичная занятость → **снижение**: закреплённый (не ротирующийся) состав команды на проект, актуальная документация по кодовой базе.
3. Минимальные резервы → **принятие пассивное + мониторинг**: заранее в SLA зафиксировано, что выходит за рамки «minor improvements», и заранее согласована процедура запроса доп. часов при обнаружении крупного бага.

**Защита:**
- Главный риск — устаревшая iOS 9: высокое воздействие (полная потеря работоспособности приложения) и растущая со временем вероятность.
- Убивает проект — Apple меняет политику App Store (например, требует минимальную iOS 13+), приложение блокируется от публикации, а бюджет/резервы контракта не предусматривают крупного апгрейда.
- Контракт → Dedicated Team/SLA закладывает минимальные резервы по определению, поэтому PM не может «тихо» покрыть неожиданные проблемы из буфера, как в Fixed Price — единственный работающий инструмент — заранее прозрачно согласовать с заказчиком процедуру эскалации нештатных ситуаций.
