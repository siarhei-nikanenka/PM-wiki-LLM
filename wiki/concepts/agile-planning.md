# Планирование в Agile

Из [[pm-13-agile-planning]].

В Agile планирование строится не на жёстких сроках, а на относительных, постепенно уточняющихся оценках — команда фокусируется не на «сколько часов», а на «сколько ценности и когда», адаптируя план по мере поступления новой информации.

## Три уровня детализации плана
- **Роадмэп** — цели и ключевые функции продукта без детализации.
- **Бэклог продукта** — полный список требований/идей, постепенно наполняется и уточняется на основе роадмэпа.
- **Бэклог спринта** — подмножество задач из бэклога продукта, взятое в работу на итерацию как «прогноз» команды (см. [[scrum]]).

## Метод набегающей волны (Rolling Wave Planning)
Ближайшие, приоритетные задачи прорабатываются детально («ближняя волна»), дальние — лишь в общих чертах. Скорее философия работы с требованиями, чем конкретная техника; эффективна при высокой неопределённости, рисках, исследовательской/R&D работе.

## Story Points
Относительная (не временная) единица оценки сложности/объёма задачи, отражает три фактора: **effort** (усилие), **complexity** (сложность), **uncertainty** (неопределённость) — в отличие от оценки в часах, которая учитывает только усилие.

## Техники оценки
- **Метод по эталону** — эталонная задача = 1 Story Point, остальные оцениваются кратно относительно неё («попугаи»); быстро, но плохо масштабируется на крупные/непохожие задачи.
- **Относительная оценка по Фибоначчи** (0, 1, 2, 3, 5, 8, 13, 21…) — разрыв растёт вместе с неопределённостью крупных задач; высокая оценка (13+) — сигнал к декомпозиции.
- **Planning Poker** — групповая техника картами (шкала Фибоначчи): скрытое голосование → одновременное вскрытие → обсуждение при расхождении → повторное голосование. Устраняет эффект «якорения» мнением лидера.
- **Оценка на пальцах** (степени двойки: 0, 1, 2, 4, 8, «веер» = пропуск/пауза) — аналог Planning Poker без карт, с более крупным шагом.
- **T-Shirt Sizes** (S/M/L/XL…) — быстрая грубая оценка для больших списков задач (например, годового бэклога эпиков) на ранней стадии, предшествует более точной оценке в Story Points.
- **Ideal Days/Hours** — оценка времени в «идеальных условиях» без отвлечений; интуитивный, но всегда оптимистичный ориентир, ненадёжен для сложных проектов.

## Velocity
Объём Story Points (или задач), закрываемых командой за спринт; считается по среднему за несколько (от 3-х) спринтов, стабилизируется со временем. Требует **постоянного состава команды** и **полной оценки всех задач** (включая баги и техдолг) — иначе метрика становится ненадёжной и непригодной для сравнения между разными командами (у каждой команды своя калибровка Story Point). Раскрывает и уточняет условия надёжности той же метрики, впервые введённой в [[velocity-metrics]].
