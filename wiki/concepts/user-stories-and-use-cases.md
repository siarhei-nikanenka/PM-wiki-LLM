# User Story, Use Case и Acceptance Criteria

Из [[pm-11-requirements-documentation]] (см. также базовое определение user story и use case в [[pm-10-scope-management]]).

## User Story

Формат из трёх частей: **«Как [роль], я хочу [действие], чтобы [цель/ценность]»**. Третья часть («чтобы») критична — без неё есть риск реализовать ненужный функционал. Пример: «Как покупатель, я хочу добавить товар в корзину, чтобы завершить покупку и оформить заказ». User story не описывает, как реализовать функцию, — она инициирует разговор, а не заменяет его.

Расширенный шаблон включает: заголовок, приоритет, оценку (story points), саму историю (as a role/I want/so that) и **acceptance criteria**.

## Acceptance Criteria — два формата

### Gherkin (Given/When/Then)
Описывает поведение системы через сценарий: **Given** — начальное состояние, **When** — действие пользователя/событие, **Then** — ожидаемый результат. Читается как естественный язык, понятен разработчикам, бизнес-аналитикам, тестировщикам и заказчикам. Часто используется и для автоматизации тестирования.

Пример (восстановление пароля):
> Given пользователь на странице входа, When выбрал «забыли пароль» и ввёл email, Then система отправляет ссылку для восстановления на этот email.

### Rule-Oriented
Список конкретных правил/ограничений, которым должна соответствовать система — удобен для интерфейсов, функциональных ограничений и бизнес-логики. Пример (поле поиска отеля): поиск начинается по кнопке, а не по вводу текста; максимум 200 символов; спецсимволы запрещены с явным предупреждением.

## Use Case — шаблон

Use case описывает диалог между пользователем и системой («игра в пинг-понг»: действие пользователя всегда сопровождается ответом системы). Поля шаблона:

| Поле | Смысл |
|---|---|
| ID | уникальный идентификатор (может совпадать с тикетом в трекере) |
| Name | краткое название сценария |
| Created by / Date | автор и дата, для отслеживания правок |
| Actor | роль, взаимодействующая с системой |
| Description | краткое описание задачи |
| Preconditions | что должно быть выполнено до начала |
| Postconditions | результат после выполнения |
| Priority | важность сценария |
| Frequency of use | как часто сценарий используется |
| Normal Course of Events | основной сценарий, шаг за шагом (пользователь → система → пользователь…) |
| Alternative paths / Exceptions | отклонения от основного сценария, ошибки |
| Includes | другие use case как часть этого (в отличие от extend на диаграмме — см. [[requirements-modeling]]) |
| Special requirements | специальные условия (например, к производительности) |

Use case не фокусируется на ценности для клиента (в отличие от user story) — только на взаимодействии пользователя и системы.
